# Agent Note: 在 DSH 内嵌 OptMem 核心并沿用原库

Status: implemented
Archived: 2026-11-25

## 问题

让 DSH 调用主机上的 Python CLI 虽然能复用老库，却把可用性绑定到外部脚本、主机 PATH 和可变的命令输出。统一模型工具不需要第二份记忆，也不应因实现迁移放宽写入授权。

## 决策

[插件](../../../../plugins/optmem/README.md) 用 Node 实现工作区定位、固定宽记录与压缩树、快照和查询，并只注册 `memo`，由 `action` 划分读操作与写操作。现有工作区身份、库路径和磁盘格式不变。查询使用可取消的 Worker，限制不可信正则在宿主内占用计算的时间。

本决策取代[单一存储与写入确认](2026-11-25-optmem-host-adapter.md)中的 CLI 适配方式；该记录的单一数据归属、会话上下文和精确人工确认仍适用。原始记录与压缩摘要只在用户同意其确切文本和目标后写入；压缩材料在锁内重验。

## 曾考虑的替代方案

**把旧脚本随包分发。** 仍依赖 Python 解释器、子进程和人类可读的 stdout 协议，没有满足独立运行的需求。

**换成独立的 DSH 数据库。** 会把工作区记忆分成两个数据源，让回退、核对和恢复依赖数据迁移。

**用同名锁假装与旧写端互通。** Node 的排他目录与旧 CLI 的系统文件锁并不能互斥。新写端独立加锁，遇到遗留锁不擅自删除，也不保证与仍在工作的旧写端并行安全。

## 后果

插件恢复和停用不搬动数据。更换写入端前需先停住另一方；同一新写端的多进程操作共享排他锁。原有文件格式和输出预算使用隔离夹具验证；运行时不需要可执行的旧脚本。
