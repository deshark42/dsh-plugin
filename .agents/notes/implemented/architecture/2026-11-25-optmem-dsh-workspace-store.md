# Agent Note: DSH 拥有独立的工作区记忆库

Status: implemented

## 问题

OptMem 的老库设计用于多入口共享，本地记录的宽度、压缩树和摘要待办因而出现在助手每次使用时。DSH 的目标变为让会话按需找回用户批准的项目背景，不需要兼容此前的 CLI 或复用其数据文件。

## 决策

[OptMem 插件](../../../../bundles/optmem/README.md) 在 DSH `data` 类目录使用独立的 SQLite 库，不向模型开放指定路径，空查不建库。存储范围见[工作区隔离决策](2026-11-25-optmem-workspace-identity.md)。

一个 `memo` 经 DSH 工具注册表服务原生执行器与 Code Mode，只公开有上限的字面子串搜索、按 ID 读取和提议保存；不管外部命令或提示词流程。[Host 人工确认](2026-11-25-optmem-host-adapter.md) 仍约束写入，由宿主核对确切文本和作用域。等确认时不占事务，批准后重新解析工作区，才由 SQLite 提交。

会话日志拥有当时发送给模型的内容；数据库只回答当前记忆。插件不挂自动注入钩子，不在恢复或 fork 时读取今天的库替换先前的上下文。主动检索的内容作为普通工具结果进入会话，而非系统指令；子代理没有新的查询入口。

## 曾考虑的替代方案

**与终端工具共用存储。** 可以让不同入口看到相同内容，但 DSH 会被原存储的布局、压缩协议和写锁约束。[早期实现](../../archived/architecture/2026-11-25-optmem-embedded-core.md) 保留该权衡。

**继续默认把工作区快照自动加入会话。** 会让普通聊天触碰长期数据，并使恢复时的行为取决于插件状态；需要开场上下文时，应只带入用户明确选择的条目，写成可追溯的会话内容，而不是系统指令。

**同时上向量搜索和自动总结。** 目前只需要准确找回短记忆；它们会引入额外模型请求、索引与审核边界，等字面搜索确实不满足实际使用再评估。

## 后果

DSH 不与旧 CLI 互通，首次使用无需旧脚本、压缩任务或自制写锁，插件可独立停用。SQLite 的已批准写入在新连接中可读取，数据不会因插件卸载被清空。

以隔离的 DSH home、profile 和工作区验证拒绝或取消不写、批准后按 ID 读回、同库并发写入、不同工作区不串读、原生/Code Mode 共用同一工具，以及不注册自动上下文的行为。真实用户数据和会话不参与测试。
