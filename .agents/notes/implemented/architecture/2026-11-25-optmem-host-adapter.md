# Agent Note: OptMem 保持单一存储，DSH 拥有写入确认

Status: implemented

## 问题

长期记忆已经由 OptMem 按工作区存放，但依赖助手记得在会话启动时执行命令，并在写入前另开一次确认。同一个工作区可能同时在 DSH 与其他终端使用，记忆的归属和存储不能随使用入口而变。

## 决策

[DSH 独立工作区库](2026-11-25-optmem-dsh-workspace-store.md) 取代了早期共用终端库和自动注入上下文的方案；[内嵌终端存储格式](../../archived/architecture/2026-11-25-optmem-embedded-core.md) 仅作为历史记录。[OptMem 插件](../../../../bundles/optmem/README.md) 的写入仍由 DSH Host 工具请求人工确认，不委托给 Bash 或提示词，也不给子代理新的读写入口。

目前写入入口是 `memo note`。DSH 的确认必须绑定目前的工作区、记忆库与实际要写入的文本；用户未确认或目标已改变时不写入。若未来重引入摘要，它同样是可被未来会话读取的持久文本，不能借此绕开确认。

## 曾考虑的替代方案

**在 DSH 另建存储。** 会让终端和 DSH 使用不同的记忆库。当时优先考虑跨入口共享；后来的[独立库决策](2026-11-25-optmem-dsh-workspace-store.md) 不再把这种互通作为目标。

**继续靠提示词规定 Bash 调用顺序。** 能直接复用 CLI，却不能由插件保证首个请求前已读取，也不能把具体写入与人类在确认卡上的选择绑定为同一次操作。

**让压缩摘要自动落盘。** 摘要仍是可被未来会话读取的持久文本，不能只因为它出自旧记录就允许未审阅的新文本。

## 后果

等待时没有写入事务；确认后的工作区变化可以单独验证。不把读取失败变成向另一位置写入，也不把超时或无答复当作许可。停用阻止新的工具调用并取消等待中的确认，不撤回已进入会话的模型输入，也不删除已保存数据。
